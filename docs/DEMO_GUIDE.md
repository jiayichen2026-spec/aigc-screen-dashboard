# 三分钟演示路径

## 0:00-0:40　看活动规模与稳定性

“这是一套面向品牌活动运营的AIGC互动大屏后台。我按参与、生成、领取、审核和设备五个环节组织信息，让运营先发现问题，再追查证据。数据完全模拟、固定快照可复现。”

默认最近7天显示857位参与者、95.02%生成成功率、38.87%扫码转化率、23.63秒平均成功时长。切换30天，展示筛选联动与趋势变化。10月4日仅截至18:00，不能与完整日直接比较。

## 0:40-1:35　从异常追查到任务

先从首屏“重点关注”查看已触发异常，再用分组导航定位“异常中心”，打开“上海生成超时增多”。失败率33.87%来自21个失败任务／62个已结束任务，不是写死的数字。展开一条任务，查看失败代码、提交与完成时间、内部尝试。

“我将观察结果、可能原因和建议行动分开。看到超时不能直接断言模型故障，需要继续核对排队和服务记录。”

翻页后点击“在概览中查看此范围”，概览定位上海10月2日至3日，成功率66.13%，与该窗口失败率互补。内部重试始终只算一个逻辑任务。

## 1:35-2:20　讲清审核与设备的差异

重置后查看杭州待审核积压：20个结果生成成功，但未审核通过前不能领取，不进入扫码分母。查看北京02设备：没有心跳属于未知，不把未知写成离线；设备始终显示固定快照。

## 2:20-3:00　展示漏斗与可复现性

重置后通过导航查看转化漏斗：878→825→782→719→692→269次体验。解释相邻转化率以各自上一阶段为分母，排队、处理中及待审核与失败分开，差额原因未知时不臆测用户放弃。说明无记录、无数据与零分母均有独立处理；指标从明细计算，不对比例做简单平均。

最后展示一页指标说明、模拟数据生成命令和79项测试。说明AI用于实现和调试，本人负责范围选择、配置、约束与验收；具体分工见AI使用说明。

## 可用于回答追问的取舍

- **为何不接数据库或真实模型？** 题目明确允许模拟数据。静态JSON让交付可复现、易部署，当前优先验证分析链路和运营决策。
- **为什么平均耗时只统计成功任务？** 保持“获得生成结果需要多久”的口径；失败和处理中单列，必须结合成功率解读，避免仅看均值。
- **为什么设备不随日期变化？** 数据只有当前心跳快照，没有完整历史心跳；不制造历史在线率。
- **后续如何扩展？** 接入真实事件和心跳后再增加历史设备状态、持续告警、权限、工单和处理记录；当前未实现这些能力。
